# Contributing

Thanks for your interest in Identity Analysis Runtime. This document covers how
to set the project up, how the test suite is split, and the rules that are
specific to a repository that handles identity documents.

## Ground Rules

Two of these are non-negotiable, because they are why the project can be public
at all:

1. **Never add real personal data.** No photographs of real people, no real
   credential, passport, or document numbers, no real names or addresses — not
   in fixtures, not in tests, not in documentation, not in commit messages.
   Every sample in this repository is generated by `tools/`. If you need a new
   fixture, extend the generator.
2. **Never add third-party model weights or SDK-derived material.** No `.onnx`
   files, no catalogs, no binaries, no decompiled or extracted data from a
   commercial identity SDK. The runtime is bring-your-own-models by design; see
   [`docs/models.md`](docs/models.md).

Beyond that: keep public response contracts stable, and never turn `review` or
`not_available` into a successful decision.

## Setup

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/pytest
```

You also need ImageMagick for HEIC conversion, and a C/C++ toolchain if no
prebuilt `zxing-cpp` wheel exists for your platform.

## Running the Tests

The suite is split by what it needs:

- **No models required.** Parsers, MRZ check digits, mask semantics, response
  shaping, barcode decoding, and everything driven by the synthetic catalog in
  `tests/fixtures/catalog`. These run everywhere, including CI.
- **Models required.** Anything that performs real ONNX inference. These are
  marked with `requires_assets` in `tests/conftest.py` and are **skipped**
  unless an asset directory is available.

```bash
# fast path, what CI runs
.venv/bin/pytest

# full suite against your own models
IDENTITY_ANALYSIS_ASSETS=/path/to/assets .venv/bin/pytest

# see what was skipped and why
.venv/bin/pytest -rs
```

An asset directory is recognised when it contains a `manifest.json`; the layout
is documented in [`docs/models.md`](docs/models.md). `assets/` in the repository
root is used by default if it exists (it is not tracked).

Some tests combine your models with this repository's synthetic catalog via the
`catalog_assets` fixture, so catalog-driven behaviour is always exercised
against data this project authored rather than against whatever catalog you
happen to have installed.

## Regenerating Fixtures

```bash
python tools/generate_synthetic_samples.py   # examples/samples/*.jpg
python tools/generate_test_catalog.py        # tests/fixtures/catalog/
```

Both are deterministic. If you change the rendered samples, the expectations in
`tests/test_pipeline_smoke.py` and friends must be regenerated by running the
pipeline against the new images — never hand-edited to whatever makes the suite
pass.

## Adding a Document

See [`docs/product/adding-documents.md`](docs/product/adding-documents.md) for
catalog layouts, document profiles, and machine-readable parsers.

## Pull Requests

1. Branch from `main`.
2. Keep the change focused, and add or update tests alongside it.
3. Run `.venv/bin/pytest`; state in the PR whether you also ran the full suite
   with models installed.
4. Update `GET /v1/capabilities` in `src/identity_analysis/capabilities.py` when
   you change what the runtime can do, and update the relevant guide under
   `docs/`.
5. Describe user-visible behaviour changes explicitly, especially anything that
   affects a decision outcome.
